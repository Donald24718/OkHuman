# `bash` 工具逻辑说明书

> **这份文档给谁看？**
> 给你 —— 用 AI 帮忙写代码、但不打算读源码的人。
>
> 你不需要懂 Go 语言。你只需要理解：**当你的 AI 助手运行一条命令时，
> 系统在背后做了什么、为什么这么做、以及为什么有些命令"跑不起来"。**
>
> 想看去代码细节的版本，请读同目录的 `README.md`。

## 一句话总览

**整个系统只有一个工具：`bash`。**

不管你的 AI 助手说它要"读文件""改文件""搜索代码""跑测试""查看日志"——
在系统眼里，这些全都是同一件事：**执行一条 bash 命令**。

这不是偷懒，是刻意的。工具越少，AI 的选择越明确，出错的面就越小。

```
你：帮我看看 config 里写了什么
AI：（内部）我调用 bash，命令是 cat config/default.json
系统：执行 → 返回文本 → 交回给 AI
AI：config 里写的是……
```

## 一、每条命令都活在一间"隔音房"里

### 发生了什么

你的 AI 每次要跑命令，系统不是直接在你电脑上跑，而是**先把命令内容写进一个临时小文件**，然后让系统去执行那个文件。

### 为什么要这么绕？

因为有些命令会"查自己人"。比如你想清理一个叫 `my-server` 的进程，命令里写着：

```bash
pkill -f my-server
```

这句的意思是"把所有命令行里带 `my-server` 的进程杀掉"。

**如果命令内容直接摊在外面**，那么执行这条命令的那个"外壳"自己，命令行里也带着 `my-server` 这几个字 —— 结果就是**它把自己也杀了**。这是真实发生过的事故：命令没清理掉目标，反而先把自己弄死了（退出码 143）。

**写进临时文件后**，命令内容藏在文件里，外壳的命令行干干净净，谁也误伤不到。命令跑完，临时文件自动删除。

> 你不需要做任何事。这是自动的。你只要知道：**系统比你想的更怕"误伤"。**

## 二、超时规则：为什么我的命令"跑到一半没了"

这是最可能让你困惑的部分，重点讲。

### 有两道"计时器"，别搞混

| 计时器 | 默认时长 | 到点了会怎样 |
|---|---|---|
| **前台等待** | 30 秒 | **不会杀命令**。只是 AI 不再傻等，转去干别的，命令继续在后台跑，跑完了再通知 AI。 |
| **总时长上限** | 600 秒（10 分钟） | **真的会杀**。不管命令在干嘛，强行终止。 |

**关键区别**：前者只是"AI 不等了"，后者才是"命令被掐死"。

### 为什么要有"总时长上限"

因为系统里跑命令是**排队**的：一条没结束，后面的全得等。

想象一个服务员一次只服务一桌。如果某桌客人赖着不走，**后面所有桌都得干等**。

真实出过这样的事故：AI 用 `nohup` 起了一个后台服务，那个服务一直"握着电话线不放"，系统以为它还没说完，就一直等 —— **等到天荒地老**，后面所有命令全部堵死。

所以必须有个"硬上限"：10 分钟到了，直接掐。

### 掐的时候，是"连窝端"

如果只掐掉领头的，它派出去的小弟（子进程）可能还在跑，还握着电话线，问题没解决。

所以系统的做法是：**整组连锅端** —— 领头的一起、小弟们一起，全部终止。这样电话线一定会断，排队一定能继续。

### 被掐死时，会告诉你原因

如果一条命令被杀，返回信息开头会长这样：

```
退出码: -1（超过 600 秒上限被强制终止；要跑更久：用 setsid + 重定向完全
脱离进程组，或调大配置 tools.timeout_ms）
```

**这不是普通的报错。** 系统特意写得这么详细，是为了让你的 AI 助手别犯迷糊 ——
否则它分不清"命令自己失败了"和"被系统掐了"，可能傻乎乎地重试同样的命令，再被掐一次。

看到这句话的意思是：**"我知道你还需要跑，但方式不对，换种方式。"**

## 三、"长驻服务"必须学会"离家出走"

上一条说到了 `setsid`，这里讲清楚。

### 什么是长驻服务

就是**会一直开着的程序**，比如：
- 一个本地网站服务器
- 一个后台监控程序
- 一个定时任务

它和"跑一下就有结果"的普通命令不同：**它永远不结束**。

### 问题来了

既然总时长上限是 10 分钟，那一个"永远不结束"的服务，岂不是**10 分钟后必然被杀**？

对。这正是设计者想要你理解的坑。

### 解法：让服务"离家出走"

在启动命令外面套一层：

```bash
(setsid <启动命令> < /dev/null > /tmp/<名字>.log 2>&1 &)
```

你不用背这串符号。**记住要三个动作一起做**：

1. **`setsid`** —— 让服务脱离原来的"家庭"，自己立户
2. **`> /tmp/xxx.log 2>&1`** —— 让它的输出写进日志文件，别占着电话线
3. **`< /dev/null`** —— 告诉它"没人给你打指令了，自己跑"

### 为什么三个必须一起做？

**只做第 1 个（只 `setsid`）会出大问题**：

服务虽然"立户"了，但还握着原来的电话线不放。系统等不到"说完了"的信号，
**依然会一直等下去** —— 而且因为服务已经"离家"，系统的超时掐人**够不着它了**。

结果就是：**10 分钟上限彻底失效，整个系统卡死。**

这比"服务被杀掉"严重得多。所以系统在给 AI 的说明书里反复强调：
**要么三个都做，要么别做。**

### 离家出走后怎么管它

```bash
curl http://localhost:端口        # 探活：问一句"你还在吗"
cat /tmp/名字.log                 # 看日志：它说了什么
pkill -f 名字                     # 叫停：不需要了
```

> **Windows 用户看这里**：上面这套是 Linux / macOS 的写法。Windows 上
> `setsid`、`/tmp`、`pkill` 都不通用，要用另一套命令 —— 详见"五之二"。
> 好消息是**"连锅端"和超时保护在 Windows 上一样有效**，要换的只是这几条命令本身。

## 四、命令输出"太长"，是怎么处理的

### 先看能不能装下

命令跑完会吐出文字。有些命令吐得极多（比如把一个几万行的日志整个打印出来）。

系统给每条命令的输出留了 **32MB 的空间**（约等于 3 千万个汉字）。

- **装得下** → 原样返回
- **装不下** → **只保留开头，后面丢掉**，并在最前面加一句说明：

```
[输出截断：仅保留前 33554432 字节，另有 12345 字节丢弃（共约 … 字节）]
```

### 为什么"丢"也要继续读

这里有个反直觉的点：**东西丢掉了，系统还得继续"看"完**。

因为命令是往一根"管子"里写字的。如果系统说"太长了我不看了"然后走开，
**管子里很快会堵满**，命令那边就写不动了 —— 它会**卡在那里干等**，永远不结束。

所以系统必须**一边丢一边继续看**，把管子里的字读走，让命令能顺畅写完、利索收工。

### 丢了的内容还能找回来吗

能。这套系统里还有另一层保护：**结果太长时，完整内容会存进一个日志文件**，
返回给你的只是"开头一部分 + 那个文件的路径"。你的 AI 助手可以再用 `bash`
通过 `cat`、`grep`、`tail` 去把全文捞回来。

**所以：看到"[已截断]"别慌，内容没丢，只是换了个地方待着。**

## 五、这些数字都可以改

如果你觉得 10 分钟不够、或者想更保守，可以改配置：

| 设置项 | 含义 | 默认 |
|---|---|---|
| `tools.fg_timeout_ms` | AI 前台最多等多久（毫秒），超了转后台 | `30000`（30 秒） |
| `tools.timeout_ms` | 命令总时长上限（毫秒），超了掐死 | `600000`（10 分钟） |

**上限有天花板**：`timeout_ms` 最多设到 24 小时。再大就没意义了 —— 那等于没兜底。

### 这里有个"聪明"的设计，值得知道

系统给 AI 看的"说明书"（也就是工具描述文字）里，超时数字不是写死的，
而是**根据你的配置现场生成**。

举例：你把上限改成 5 秒，AI 看到的说明书里就会写"超 5 秒被强制终止"。

**为什么这么做？** 因为如果配置能改、说明书却写死旧数字，AI 就会**照着假数字做决定**
（比如它以为有 10 分钟，实际只有 5 秒，于是放心跑长命令结果被掐）。

系统宁可让一份缓存作废，也要保证：**AI 看到的数字，就是真实生效的数字。**

## 五之二、在 Windows 上用也一样（"连锅端"换了把工具）

前面说的道理**在 Windows 上原样成立**，但具体"工具"不同。你不需要记细节，
只要知道**该保护的都保护了**：

| 做的事 | Linux / macOS | Windows |
|---|---|---|
| 把命令关进"隔音房" | 临时文件 | 临时文件（同一个机制） |
| "连锅端"杀整棵树 | 独立进程组 + `kill(-pid)` | **Job Object**（Windows 内核的"集装箱"） |
| 判断"是被我们掐死的吗" | 看进程是否死于信号 | 看退出码（换了套判据，结论同样可靠） |

**三个你要知道的 Windows 差异**：

1. **"离家出走三件套"在 Windows 上不通用**。`setsid` 是 Linux 专有；
   Windows 上让服务长驻要用别的写法（如 PowerShell 的 `Start-Process`）。
   **遇到这个问题，直接问你的 AI"Windows 上怎么让服务脱离"，它会给你正确写法。**
2. **路径写法不同**。Windows 上临时文件在 `%TEMP%`（类似
   `C:\Users\你的名字\AppData\Local\Temp`），不是 `/tmp`。
   日志文件也建议放这里或你指定的目录。
3. **"连锅端"更彻底**。Windows 的 Job Object 是内核级的 —— 服务想"偷偷派个小弟跑掉"
   也逃不掉，比 Linux 的进程组更严密。

> **对你的意义**：如果你在 Windows 上跑 OkHuman，前面那五道保险**一道都没少**。
> 唯一的区别是"离家出走"的具体命令要换 —— 那本来就是 AI 该帮你决定的事。

## 六、一句话记住每件事

| 你可能遇到的现象 | 真实原因 | 你该做什么 |
|---|---|---|
| 命令"没反应"了很久 | AI 前台只等 30 秒，之后转后台了 | 别急，等通知，或催 AI 去查后台任务 |
| 命令跑一半被杀 | 超过了总时长上限（默认 10 分钟） | 让 AI 用"离家出走三件套"重启，或调大配置 |
| 看到"[输出截断]" | 输出超过 32MB | 内容在日志文件里，让 AI 去捞，别重跑 |
| 启动的服务器很快就挂 | 没做"离家出走"，被超时连坐了 | 提醒 AI 用 `setsid + 重定向 + < /dev/null`（Linux）或对应的 Windows 写法 |
| 看到"[平台降级]" | 系统没拿到最强的"连锅端"能力，退而求其次 | 一般不影响用；若关心，告诉 AI 看这条提示 |
| 命令自己把自己杀了 | 老问题，现已修复（命令写进临时文件） | 一般不会遇到了 |

## 七、最后：写给"只会用 AI"的你

这套机制的存在，本质上是在回答一个问题：

> **当 AI 说"我来跑条命令"时，怎么保证它不会把整个系统拖死？**

答案就是这五道保险：

1. **命令藏进临时文件** —— 防误伤自己
2. **超时会连锅端** —— 防一条命令堵死全场
3. **超时信息写清楚** —— 防 AI 傻乎乎重试
4. **输出封顶但继续读** —— 防大输出卡死
5. **长驻服务可"离家"** —— 给真的需要长期运行的东西留活路

**这五道保险 Windows 上同样生效**（见"五之二"），只是"连锅端"的底层换了工具。
**你不需要操作任何一项。** 它们是自动的。

你只需要在 AI 助手"卡住"或"命令被杀"的时候，能看着这份文档说一句：

> "哦，这是超时了，你试试让它离家出走。"

—— 那这份文档就起到作用了。
