# scout 的教训（2026-11-05，改向量/加 keywords 这一轮）

1. **别从"字段名"猜类型。** `meta.json` 的 `keywords` 在 `multi-gpu-torch` 里是**数组**，我按 `string` 解码 →
   `json.Unmarshal` 整个失败 → 那条被**静默丢掉**，索引 26 变 25。修法不是加判空，是**容错解析 + 把失败记进 problems**
   （`/reindex` 报 `meta_problems`、`/doctor` 列明细）。同类旧错：`str.lstrip('</div')` 从文本前缀反推语义。
2. **"少一条"只能靠可对照的证据发现。** 修好我的办法就是 `/doctor`：当场重扫 + 与内存索引对照，报
   `stale_in_index / missing_from_index / no_keywords / same_name / meta_problems`。索引这类派生数据必须自带自检面。
3. **先测再定方向。** 我一度断定"向量没用因为召回差不多"，又一度断定"要去掉单字分词"——两次都被数据打回：
   真正的杠杆是**字段里有没有那个词**（`keywords`）。带向量 R@1 24/34、纯关键词 22/34、补 keywords 31/34；
   留出集 6/12 → 8/12。去单字：R@1 22→20，不采纳。**没有对照集的结论不算结论。**
4. **动手前先看清现场。** 我这轮连着三个低级错：说"scout 没有版本管理"（它早有独立 git，7 次提交）；
   没读就覆盖了 `.gitignore`（原有 5 条）；把 `git push` 跑在了错误的仓库里。都属于"先动手后看"。
5. **别把设计往上加。** 本轮从"增量 + 持久化表 + 压实 + 稳定 id + redirect + 同名定主 + 倒排"一路被主人的追问削到
   "无向量 + 内存索引 + keywords 字段"，每一步削减都有实测或明确否决。**先给最小可验证形态，再按需要加**。
