# agent-wire — 异步、搭车与取正文的判据

## 异步与搭车（发送方仍在干活时对方跑完）

`send` 一律**不等**：派完立刻返回，同时起一个**跑完就退出**的一次性 watcher（`wait-inject`，日志落 `<实例数据目录>/agent-wire/waiting/<id>.log`（数据目录由实例声明注入，见 `config.md`；未声明时退回可执行文件同目录的 `data/`）；等待记录 `<id>.json` 里存 watcher 的真 pid——任务 ID 里那个 pid 是 send 那一刻的短命进程，判不了活死）。对方 `run_end` 后正文以 `POST /enqueue` 投回发送方（投不动就落 `data/undelivered/`，下次任何调用会补投——2026-11-10 前只落盘不补投），经主程序的**轮内搭车**（`TakePendingUsers`）进入发送方**当前这一轮**。

watcher 被打断（发送方重启、机器重启、OOM）→ **任何一次调用**都会按 pid 发现它没了并**重新接上**（≤5 次，第 6 次投「等不到」并删记录）；`pending` 报 watcher 活死。2026-11-10 实测：派活 2 秒后杀掉 watcher，下一次 `list` 接上，仍取到完整正文并 `run_end` 收口。

## 事件游标与输入匹配

- 取正文靠**事件游标**：先 `GET /events/poll?since=-1` 记下基线（只为省流量），之后只看新批次 → 累加 `delta.text`。**分清是不是发送方这一轮：靠输入匹配，不靠游标。**
  **游标只能按"已读到的批"推进，绝不能用响应里的 `latest` 推**：单次 poll 最多给 50 批（服务端 `maxPollBatches`），`latest` 是对端窗口最新批号，拿它推游标会跳过没读的批——2026-11-10 实测 63 批的一轮只收到前 48 段且错过 `run_end`。响应里的 `gap`＝被窗口挤掉的批数，必须计进回信说明（"有 N 批没取到，正文可能不完整"），不许交出一段看着完整的截断正文。
- **只认"输入里含本次任务原文"的那一轮**：服务端每轮开始广播 `run_msg`（本轮实际输入全文，合并批次形如 `【第 N 条】…`，原文不改），轮内搭车时广播 `user_piggyback`（原文也不改）→ 两者任一含本次任务原文，那轮的 `run_end` 才是给发送方的；**之前的 `run_end` 一律忽略**。对方空闲但未认出输入时，先读 `/queue`：本次任务还在队列里＝没轮到它，继续等（不拿旧正文交差）；已不在队列＝接上太晚，才兜底取 `/history` 并标明"可能不是给发送方的"。2026-11-10 实测：别人的轮在前→取到本次任务对应的回答；被搭车→取到含本次任务的那轮；一直排队→不投递。

## 等待与收口（2026-11-10 定）

- `CHECK_WIN=10800s` 是**取一次并续期**的窗口，不是放弃时限；只有**连续不可达 ≥5 分钟**才终止并报「无回信」（按次数判会在跨机抖动时误杀）。窗口到点而对方仍在 run → 投 `【agent-wire 仍在等 · 来自 X】`、把末条消息当**中途状态**报出（不算回信），然后续期再等三小时。
- 收口条件：`run_end`，或 poll 响应里的 `running=false`（与帧同锁同刻，不用再打 `/status`）——且**必须已取到过本游标之后的帧**，否则可能把还没开始的一轮当已结束。
- 取正文的次序：①事件流累加；②有缺口或没认出输入时，去 `/history` **定位含本次任务原文的 user 条目，取同段它之后最后一条有正文的 assistant**；③再不行才取 `/history` 末条并标明"可能不是给发送方的"。取到什么**一律标明类型**（正文 / 思考 / 工具结果 / 输入）。
- `/history` **没有 `limit` 参数**，响应必是全量（含 reasoning），故大响应走 30s 超时客户端。
- 实测教训：只认事件流会漏（接上晚就错过 `run_start`）；对端转后台后 `running` 会长期为 true，所以要能报中途状态而不是死等。
