# agent-wire — agent 之间互发消息（跨机）

让一个 agent 在自己的回合里**问另一个 agent**，并拿到**对方那一轮的最终正文**。无守护进程：`send` 查状态+投递后立刻返回，取正文交给一次性子进程（见下 §异步与搭车）。

## 用法

```bash
W="plugins/agent-wire/agent-wire"
$W list                                    # 有哪些 agent、谁在线、谁在 run（只读，任何时候可调用）
$W send 另一实例 "…消息…"                 # 名字之后一律是正文（含以 - 开头的列表项）；没有 --wait/--json
```

## 异步与搭车（我干活时它跑完了）

`send` 一律**不等**：派完立刻返回，同时起一个**跑完就退出**的一次性 watcher（`wait-inject`，日志落 `data/waiting/<id>.log`；等待记录 `<id>.json` 里存 watcher 的真 pid——任务 ID 里那个 pid 是 send 那一刻的短命进程，判不了活死），
对方 `run_end` 后正文以 `POST /enqueue` 投回发送方（投不动就落 `data/undelivered/`，下次任何调用会补投——2026-11-10 前只落盘不补投），经主程序的**轮内搭车**（`TakePendingUsers`）进入发送方**当前这一轮**。watcher 被打断（发送方重启、机器重启、OOM）→ **任何一次调用**都会按 pid 发现它没了并**重新接上**（≤5 次，第 6 次投「等不到」并删记录）；`pending` 报 watcher 活死。2026-11-10 实测：派活 2 秒后杀掉 watcher，下一次 `list` 接上，仍取到完整正文并 `run_end` 收口。

回信头部**由插件拼**（发送方不参与写）：`【agent-wire 回信 · 来自 <对方名>】` + `任务：<原消息前 80 字>` + 对方那一轮正文；窗口到点仍在 run 投 `【agent-wire 仍在等 · 来自 X】`，连续不可达投 `【agent-wire 无回信 · 来自 X】`（没有"回信超时"这种字样）。

- **它回信里说"已完成/已核对"，仍要从控制侧复核**（远端自己说成功不算）。复核只需一条命令的量：目标文件的 mtime 是否还是我改的时刻、备份在不在、真 `diff`、被服务单元的 `MainPID`/`NRestarts` 有没有变。2026-11-08 与另一实例互相通报 8080 自启修复，两侧都对得上——但"对得上"是复核出来的，不是它说的。多个 agent 各派任务时，靠前缀 + 任务原文对上。

## 规则（硬）

- **只能给空闲的 agent 发**：发前读对方 `/status`，`running=true` 就拒绝（退出码 2）。注意这只是**我查的那一刻**空闲——查状态与投递是两次请求，中间它可能被别人的消息点着（最常见是用户在那台界面上回车）；真正的保证来自下一条的轮次归属，不是这条预检。
- **不能给自己发**：自己此刻必然在 run，规则本身就该拒。
- 取正文靠**事件游标**：先 `GET /events/poll?since=-1` 记下基线（只为省流量），之后只看新批次 → 累加 `delta.text`。**分清是不是我这一轮靠下面的输入匹配，不靠游标。**
  **游标只能按"已读到的批"推进，绝不能用响应里的 `latest` 推**：单次 poll 最多给 50 批（服务端 `maxPollBatches`），`latest` 是对端窗口最新批号，拿它推游标会跳过没读的批——2026-11-10 实测 63 批的一轮只收到前 48 段且错过 `run_end`。响应里的 `gap`＝被窗口挤掉的批数，必须计进回信说明（"有 N 批没取到，正文可能不完整"），不许交出一段看着完整的截断正文。
- **只认"输入里含我这条"的那一轮**：服务端每轮开始广播 `run_msg`（本轮实际输入全文，合并批次形如 `【第 N 条】…`，原文不改），轮内搭车时广播 `user_piggyback`（原文也不改）→ 两者任一含我的任务原文，那轮的 `run_end` 才是给我的；**之前的 `run_end` 一律忽略**。对方空闲但我没认出输入时，先读 `/queue`：我那条还在队列里＝没轮到我，继续等（不拿旧正文交差）；已不在队列＝我接上太晚，才兜底取 `/history` 并标明"可能不是给我的"。2026-11-10 实测：别人的轮在前→取到自己那条的回答；被搭车→取到含自己那份的那轮；一直排队→不投递。
- 等待语义（2026-11-10 改）：`CHECK_WIN=10800s` 是**取一次并续期**的窗口，不是放弃时限；只有**连续不可达 ≥5 分钟**才终止并报「无回信」（按次数判会在跨机抖动时误杀）。窗口到点而对方仍在 run → 投 `【agent-wire 仍在等 · 来自 X】`、把末条消息当**中途状态**报出（不算回信），然后续期再等三小时。收口条件：`run_end`，或 poll 响应里的 `running=false`（与帧同锁同刻，不用再打 `/status`）——且**必须已取到过本游标之后的帧**，否则可能把还没开始的一轮当已结束。取正文的次序：①事件流累加；②有缺口或没认出输入时，去 `/history` **定位含我这条原文的 user 条目，取同段它之后最后一条有正文的 assistant**；③再不行才取 `/history` 末条并标明"可能不是给我的"。取到什么**一律标明类型**（正文 / 思考 / 工具结果 / 输入）。注意 `/history` **没有 `limit` 参数**，响应必是全量（含 reasoning），故大响应走 30s 超时客户端。实测教训：只认事件流会漏（接上晚就错过 `run_start`）；对端转后台后 `running` 会长期为 true，所以要能报中途状态而不是死等。

## 派活的措辞（硬规矩，2026-11-07 用户定）

`/enqueue` 不带来源（`QueuedMessage` 只有 `{Text, Kind}`）→ 对方收到的就是一条普通 user 消息，**分辨不出来自谁**。所以：

- **用用户的口吻直接下指令**：要做什么 + 参数 + 交付物 + 验收标准，一次写完。
- **不要自我介绍、不要写"某 agent 令我们…／这是某 agent 派来的"**：跨实例派活默认已有用户授权，正文不必交代来源。
- 实测反例（2026-11-07）：开头写「【本实例 派的活】…用户令我们五个各画各的」→ 另一实例判成第三方转述，按规矩不执行不承诺，连回两轮"等用户一个字"；小黑、小鲸没看出来，就当成用户的话做了。**同一条消息两种结果，差别只在措辞。**
- 别绕：不复述对方的规矩、不署名；要留痕就让它把产物写进指定目录，事后按文件核。
- 不一定走本插件：直接 `POST http://<实例>/enqueue {"message": …}` 效果相同（这次我就是这样发的），措辞规矩同样适用。
## 配置（config.json，与可执行文件同目录）

```json
{"self": "小A",
 "peers": [
   {"name":"小A","url":"http://127.0.0.1:8451"},
   {"name":"另一实例","url":"http://127.0.0.1:8452"},
   {"name":"小B（跨机）","url":"http://<对方主机>:8602","token":"<对方 lan-bridge token>"}]}
```

- 本机实例直连 `127.0.0.1:<port>`；**跨机走对方的 lan-bridge**（带 `token`，用 `Authorization: Bearer`）。
- 桥的白名单需要 `/status`、`/events/poll`、`/enqueue`（默认已放开）。

## 构建

```bash
cd "<本目录>" && go build -o agent-wire agent-wire.go   # 只用标准库
```

## 排障

- `拒：X 正在 run` —— 正常：规则如此。要等就自己隔几秒再试一次（`list` 可先看状态）。
- 拿不到正文但对方确实跑了：多半是对方只发 `delta` 没有 `text`——本插件按 `delta.text` 累加，若主程序改了事件形态，先看
  `curl -H "Authorization: Bearer <token>" "http://<桥>/events/poll?since=0"` 里 `frames` 的真实形态（一帧是整块 SSE，要按 `data:` 行解析）。
- 跨机不可达：先确认对端的 lan-bridge 在听（`ss -ltn | grep 860`）与 token 正确。
- 接上的 watcher「一秒就没了」、记录还留着而日志不见：多半是等待记录被**非原子**重写（先清空再写），刚起来的 watcher 读到空文件、`Unmarshal` 失败就静默退——写记录一律临时文件 + `rename`（2026-11-10 修）。判断进程活死看 `/proc/<pid>`，别用 `pgrep -f`（本场景数不准）。
