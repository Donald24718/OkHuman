## 二、逐条实证

### 1. `DoomWarnAfter <= 0` → panic ✅ 致命

`runLoop` 每个工具调用都走 `isSameRunLocked(opt.DoomWarnAfter)`：

```go
if len(a.lastCalls) < n { return false }   // n=0 → false（不返）
tail := a.lastCalls[len(a.lastCalls)-n:]   // n=0 → 空切片
first := tail[0]                           // 💥 index out of range
```

- `n = 0`：`len < 0` 为假 → 空切片取 `[0]` → panic；
- `n < 0`：`len - (-1)` 越界 → panic。

**可达性实证**：`DoomWarnAfter` 来自 `cfg.Doom.WarnAfter`（`server.runOpt`），
`config/default.json` 是 3，但 `doom.warn_after` 是 `user.json` / `POST /config` 可写的
**任意整数**——配置里写 0 就能打挂实例（`MaxToolRounds` 有 `maxToolRounds()` 兜底，
`DoomWarnAfter` 是唯一没兜的那个）。

**修复**：`normalizeRunOptions`（入口统一兜 3）+ `isSameRunLocked` 内 `n <= 0` 防御
（判定函数不该假设调用方合法）。守护：`TestIsSameRunLockedRejectsNonPositiveN`、
`TestDoomWarnAfterZeroStillRuns`。

### 2. 4xx 阶梯：先 `ForceHardTruncate` 再 `Compose` ✅ 高危

旧代码：

```go
default:
    messages, demoted = a.cm.ComposeWithDemotion(nil)   // ① 先组装
}
if mode == fbTruncate { a.cm.ForceHardTruncate() }      // ② 后截断
err2 := a.streamOnce(callCtx, client, messages, ...)    // ③ 发的还是 ① 那份
```

`ForceHardTruncate` 改的是 `cm.session`（`hardTruncateLocked` 切 Messages + 换 Summary），
**不会回溯修改已经组装出来的 `messages` 切片**（`ComposeMessages` 返回的是新切片）。
所以第三级"兜底"发的仍是被拒的超长请求 → 几乎必然再 4xx → 阶梯耗尽。

**实证**：`TestHardTruncateHappensBeforeCompose` —— 塞 10 条 ×2 万字符（20 万字符，
`HardTruncChars=5 万`），首次请求 11 条消息，断言重试请求条数**必须变少**。
把两行换回旧顺序 → 例变红（实测变红）。

### 3. `systemPrompt` 死字段 ⚠️ 部分成立（报告的结论错了，但病是真的）

- 报告说"热更新大概率无效"——**不成立**：`cm.SetSystemPrompt` 存在且被 server 调用
  （`server.go:625/657` 两处都是 **先 `CM().SetSystemPrompt` 再 `Agent().SetSystemPrompt`**），
  `composeLocked` 用 `m.systemPrompt` 组装 → 热更新实际是生效的。
- 但"只写不读的字段"**是真的**：`a.systemPrompt` 全仓无人读（grep 确认）。
  这类字段是下次热更新失效的伏笔——下一个人照 `SetSystemPrompt` 的名字改，不会知道
  真正生效的是 `cm`。

**修复**：删掉 `Agent.systemPrompt`，`New` 去掉该参数，`SetSystemPrompt` 直接委托
`a.cm.SetSystemPrompt(p)`。系统提示词从此只有 `cm` 一个真相源。

### 4. 异常截断重试 ✅ 中危（两处）

- **上下文缺失**：`retryTruncation` 只注入一句"你上一条响应有思考内容…"，但那条
  assistant 消息**根本不在会话里**——`llmCall` 不落消息（只有 `finishText`/`finishStopped` 落）。
  对无状态 LLM 来说，这句话没有对象；且前端已经把这段思考显示给用户，会话里却没有。
- **脏 delta**：第一次的思考增量早就 `emit` 出去了，重试前没有 `delta_reset`
  （4xx 阶梯有 `rollbackPartial`，这条路径漏了）→ 前端拼出"半截思考 + 重试正文"。

**修复**：重试前 `emit(delta_reset)`；把被判定截断的那次响应以
`assistant{Content:"", ReasoningContent: thinking}` 落会话后再注入提示。
守护：`TestTruncationGiveUp`（新增断言：会话里必须有那条带 thinking 的 assistant 消息）。

### 5. 轮次上限丢弃 `resp.ToolCalls` ❌ 不成立（不改）

报告的推论是"上下文里缺少它刚刚请求工具这一事实"。**复核会话序列**：

```
… assistant(tool_calls A) → tool(A1) … tool(An)     ← 上一轮已完整配对
  → user("本轮工具调用已达上限 N 次…") → tailCall
```

触达上限时 `resp`（带 tool_calls B）不存，但**上一轮**的 assistant + tool 结果已完整配对，
没有悬空 tool_call，协议合法（既有 `assertToolCallsPaired` 在 `TestToolRoundLimitStopsRunawayLoop`
里就是绿的）。
反过来，若把 B 存进去，就**必须**为 B 的每个 call 补合成 tool 结果，否则严格校验端点直接 400；
而"已达上限"的合成结果只是噪音。

**处置**：不改代码，加注释写明"有意不存"及理由，避免下一个人又"修"回去。

### 6. doom 警告名 + `warned` 复位 ✅ 中危（比报告写的更严重）

- **点名错**：批末 `warnName = a.lastCalls[len-1].Name`。`A,A,A,B` 批次里重复的是 A，
  警告却说 B —— 已复现。修：触发 `doomWarnPending` 的那一刻就记下 `tc.Function.Name`。
- **更严重的是复位**（报告只说"威慑被削弱"）：旧代码在**同一批里**先 `warned = true`，
  转身又因尾部是 `A,A,B` 判定 `sequenceBroken` 把它清掉。后果不只是"警告内容错"——
  模型只要**每批末尾换一个调用**就永远停在警告档、**永远触发不了 `doom_stop`**
  （下一批 A,A,A 又只警告一次）。这是 §8 强停机制的一个真漏洞。

**修复**：`sequenceBroken := !needWarn && !isSameRunLocked(...)`（刚警告过的批次不复位）。
守护：`TestDoomWarnNamesTriggeringTool` —— `A,A,A,B` 后接 `A,A,A` 必须点名 alpha 且
`doom_stop` 恰好 1 条（两条变异各自都能让例变红，实测均变红）。

### 7~11：run_end 顺序 / StartedAt / recover / 默认值 / 空响应 ✅

- **7**：`run_end` 在 `offCompress`/`runCancel` **之前**发出，期间若还有压缩流出，
  前端已认定本轮结束却又收到本轮 `compress`。修：收尾顺序改为"拆监听 → `SetRunSignal(nil)`
  → `runCancel` → 最后 `emit(run_end)`"。守护：`TestRunEndEmittedAfterCleanup`
  （在 `run_end` 的回调里同步调 `cm.ForceHardTruncate()`，若监听没拆就会出现
  run_end 之后的 compress 事件）。
- **8**：`startedAt` 在 `case <-fgTimer.C` 里取 = 工具启动 + `FgTimeoutMS`；
  `background.go` 的 `DurationMs = now - StartedAt` → **永远少算一整段前台等待**。
  修：挪到 `go func()` 之前。守护：`TestBackgroundStartedAtCoversForegroundWait`
  （`bash sleep 2` + 前台 400ms，断言 `StartedAt` 与 `tool_call` 时刻差 < 200ms）。
- **9**：工具 goroutine 无 `recover` → 工具实现 panic 会打挂整个进程。已加
  `defer recover()` 转成「工具失败」文本（与 `ExecuteTool` 返回 error 同一条路）。
  注：本机无法自造工具 panic（`ExecuteTool` 只分发 bash/ipython），此条为代码审查结论，
  未配变异测试——已在表中如实标注。
- **10**：`normalizeRunOptions` 兜 `DoomWarnAfter=3` / `ResultLimit=50000` /
  `FgTimeoutMS=tools.DefaultFgTimeoutMS`（**复用工具层常量，不另写数字**）/ `DataDir` 空 → 临时目录。
  实证后果：`ResultLimit=0` 时每个工具结果都被截成只剩一句提示；
  `FgTimeoutMS=0` 时 `select` 与 `execDone` 同时就绪 → **随机**分支（同一命令有时正常回填、有时转后台）。
- **11**：空正文 + 无 tool_calls（异常截断放弃轮 / 模型直接给空响应）→ `finishText` 原样返回空串。
  修：统一用 `noContentReply`，且**返回值与落会话文本同源**（与 `finishStopped` 同口径）。
  `TestTruncationGiveUp` 的既有断言（期望空串）已按新行为更新。

### 12：`writeToolLogOK` 绝对路径 ✅（反引号不修）

`filepath.Join(相对 DataDir, …)` 出来的也是相对路径，而"返回绝对路径"是它对模型的契约
（提示里让模型 `cat` 那个路径）。修：`filepath.Abs`（失败则保留原值）。
报告同时提的"反引号包裹不安全"（路径含反引号）——**不修**：Windows/Unix 用户目录下出现
反引号的概率极低，为它引入 shell 转义分支的复杂度不划算，记录在案即可。

### 13："并行工具调用"实为串行 ⚠️ 现象成立，结论不采纳

现象没错：循环里 `go func()` 之后立刻 `select` 等它，多个 tool_call 是排着队跑的
（只有前台超时转后台的那个会与后续调用重叠）。
但**改成真并发不是更优解**：bash 共用一个工作目录、ipython 共用一个常驻内核——
两段代码在同一内核上交错执行语义不可控，两条命令同时改同一个文件更是直接踩踏。
**处置**：保留顺序执行，把注释从"并行工具调用也按序回填"改成明确的
"逐个顺序执行（有意如此）…"，消除误导。

### 14：靠前缀识别后台通知 ✅ 已结构化

`bgNoticePrefix` 是用户可控文本：用户消息以那句中文开头就会被当成系统通知、不加
`【用户追加】` 前缀。
修：`PendingMessage{Text, System}`；`server.MessageQueue` 改 `[]queuedMsg{Text, System}`，
`enqueueAndWake` 增加 `system` 参数（后台 settle 通知传 `true`，三个入口传 `false`）；
`bgNoticePrefix` 降级为纯文案常量（成为 `FormatBackgroundNotice` 的唯一来源）。
前端 `user_piggyback` 同步改为优先用 `data.system`，文本前缀仅作兜底（老帧兼容）。
守护：`TestPiggybackUsesStructuredKind`（用户消息冒用通知前缀也必须加 `【用户追加】`）。

### 15：`Stop` 与 run 起始的布尔复位 ❌ 不成立

`stopRequested` 在新 run 开始时复位，语义上就是"停止只作用于**在飞**的那一轮"——
用户在一轮结束之后按 `/stop`，本来就不该杀掉下一轮。报告描述的"stop 丢失"正是期望行为。
引入 runID/代际能挡住的是一个不存在的语义错误，反而增加状态。**不改**。

### 16：defer 注释与 LIFO 相反 ✅

注释写"先清字段"，实际 LIFO 是**先 `callCancel()` 后清字段**——而且实际顺序才是对的
（先清字段会让 `Stop()` 在窗口里拿到 nil、漏掉中断）。修注释。

# 五、二次反思（2026-10-06 晚）—— 对"上一轮修复"的第一性原理复查

上一轮是**照着审查报告逐条打勾**：报告说"加归一化"，就加归一化。打勾式修复的危险在于
只验证"报告指出的现象消失"，不问"这个改动本身引入了什么"。本轮抛开报告，只问一件事：

> **每个参数取每个值时，代码的语义应该是什么？现在的代码是不是那个语义？**

复查时发现上一轮的归一化自身埋了两处缺陷，都源于同一个错误前提：

> ❌ 前提："0 / 负数 / 空串 = 非法值，应该兜成默认。"
>
> ✅ 事实：`RunOptions` 的值全部来自 `config/default.json`（三项都齐：3 / 30000 / 50000）
> 经 `server.runOpt` 现取。所以 **0 只可能是用户在 `user.json` 或 `POST /config` 里
> 显式写的**——那是意图，不是缺失。把它改写掉等于替用户做决定。

## 5.1 `doom.warn_after: 1` → 第一次工具调用就吃警告（语义灾难）

`isSameRunLocked(n)` 问的是"最近 n 次调用是否完全相同"。

| n | 数学语义 | 实际行为 |
|---|---|---|
| 0 | 空序列 | tail 为空切片 → `tail[0]` **panic** |
| 1 | 单元素序列**恒等于自身** | **恒 true** → 第一次调用就被警告"你已连续 1 次…" |
| ≥2 | 正常 | 正常 |

上一轮只防了 0（panic），漏了 1。**实测**（`TestProbeDoomWarnAfterSemantics`）：

```
DoomWarnAfter=1：警告=true    ← 第一次调用就警告
```

且上一轮把 `0 → 3` 归一化，与函数内 `n <= 0 → false`（= 不检测）**语义自相矛盾**：
归一化后 n 恒 > 0，那行防御成了死代码，而用户"关掉检测"的意图被静默改写掉。

**修正**：`n < 2` 一律判"不是"（同时覆盖 0 的 panic 与 1 的荒谬），并**撤销**对
`DoomWarnAfter` 的归一化——0/1 = 关闭检测，这是合法的用户意图。

## 5.2 `DataDir` 为空 → 日志落进**进程当前工作目录**（上一轮引入）

上一轮为满足"返回绝对路径"的契约加了 `filepath.Abs`。空 `DataDir` 时：
`filepath.Join("", "tool-results")` = `tool-results` → `Abs` 解析成 **cwd**。

**实测**（探针直接调 `writeToolLogOK`）：

```
DataDir 空 → path="D:\Project\OkHuman\internal\agent\tool-results\tool-….log"
```

文件**真的被写进了源码目录**（已清理）。契约上"绝对路径"满足了，但落的是一个完全错误、
还会污染仓库的位置。而归一化里那句 `DataDir = "" → os.TempDir()` 根本没生效——
`writeToolLogOK` / `formatTruncated*` 可以绕过 `Run` 入口被直接调用。

**根因**：把不变量放在入口（`normalizeRunOptions`），依赖"所有调用方都先跑过归一化"
这个**隐含契约**。第一性原理：**不变量要在被使用的地方强制。**

**修正**：`writeToolLogOK` 就地禁止——`DataDir` 空 = 不落盘、返回失败，不创建任何目录；
提示文案走已有的"落盘失败"分支（如实告知"全文不可找回"，不给假路径）。撤销 `os.TempDir()` 兜底。

## 5.3 仍然保留归一化的两项（及论证）

归一化会改写用户值，所以每一项都必须说明理由，不能笼统说"兜成合法值"：

| 项 | 为何 0 不是合法意图 |
|---|---|
| `ResultLimit` | 0 = 每条工具结果都被截成空字符串，任何下游都无从工作 |
| `FgTimeoutMS` | 0 = `time.NewTimer(0)` 立刻到期，与 `execDone` 同时就绪，`select` **随机**二选一 → 同一条命令有时回填真实结果、有时转后台，行为不确定 |

# 六、第三轮反思 —— 审"上一轮的修正"本身

上一轮的结论是两条铁律：**① 0 可能是用户意图，不该一律归一化**；
**② 不变量要在被使用的地方强制**。本轮拿这两条反过来审上一轮自己的改动。

## 6.1 铁律②执行得不彻底：只做了 `DataDir`，漏了同类项

## 6.3 耦合陷阱：内存保护被绑死在检测阈值上

`trimCallRecs` 的窗口大小直接取 `doomWarnAfter + 1`，且 `n <= 0` 时**直接 return 一条不裁**。

第一性原理：**"防止内存无界增长"与"检测阈值是多少"是两个正交关注点**，
不该被同一个参数绑死。新增 `maxCallRecs = 64` 硬上限，keep 夹到 `[2, 64]`。

# 七、第四轮反思 —— 上一轮在**错误的维度**解决问题

第三轮我给 `trimCallRecs` 加了 `maxCallRecs = 64` 硬上限，理由是"防止内存无界增长"。
本轮先问一句：**这个上限有没有副作用？**

## 7.1 上限把检测能力一起裁掉了（第三轮引入的回归）

`isSameRunLocked(n)` 需要**尾部 n 条**才能判定。窗口只有 64 条时，
`doom.warn_after > 64` → `len(lastCalls) < n` 恒成立 → **检测永久失效**。

**实测**（`TestProbeDoomDetectableAtLargeThreshold`，连续 n+50 次完全相同调用）：

```
doom.warn_after=100：连续 150 次相同调用却检测不到（滑窗只剩 64 条）
doom.warn_after=200：连续 250 次相同调用却检测不到（滑窗只剩 64 条）
```

用户把阈值从 3 调到 100，本意是"更宽容一点"，实际效果是**彻底关掉死循环检测**
——与他的意图完全相反。这是个典型的"修复引入的回归"。

## 7.2 根因：内存瓶颈在"每条多大"，不在"保留几条"

**实测**（`TestProbeCallRecKeyIsBounded`）：一条 100KB 的 bash 命令 →
`stableKey` 产出 **100018 字节**。

而 `callRec.Key` **只用于相等比较**（`isSameRunLocked` 里 `c.Key != first`），
从不展示、从不解析——存完整参数 JSON 纯属浪费。

于是正确的修法在另一个维度上：**让每条记录定长**，而不是限制条数。

| | 旧（完整 JSON） | 新（定长摘要） |
|---|---|---|
| 单条 Key | 随参数线性增长（实测 100018 B） | 固定 `len(name)+33` B |
| 1000 条内存 | 可达数十 MB | ~40 KB |
| 窗口大小 | 必须靠 64 上限保命 | 不受内存约束 |

`stableKey` 改为 `name + ":" + hex(sha256(json)[:16])`：语义不变（Go 的 map JSON
序列化自动键排序 → 同参数必得同摘要），内存与参数长度脱钩。
`maxCallRecs` 随之从 64 放宽到 4096 —— 只用于防荒谬配置，不再是省内存的手段。

## 7.3 元教训：我的测试偏向了我当时的结论

第三轮我写了 `TestProbeTrimCallRecsBounded`，只断言"裁剪后 `len(rc) <= 64`"。
它**完美地验证了我想要的性质**（有界），也**完美地掩盖了我破坏的性质**（够用）。

> ⚠️ 修 bug 时写的测试，天然会偏向"这次改动想要的效果"。
> 必须同时断言**相邻的不变量**——这次是"裁剪后仍够 `isSameRunLocked(n)` 用"。
