# OkHuman — 项目总览

> 核心思想 / 架构亮点 / 插件机制 / 部署拓扑。

## 一、核心思想

- **一个进程 = 一个 agent**：Go 单仓（main.go + internal/ + webui/ + prompts/），一个进程就是一个完整 agent——系统提示词、消息队列、上下文管理、工具循环、WebUI 全在一个进程里。多 agent = 多个独立端口的进程，没有框架、没有共享状态。
- **一个元工具（bash）**：agent 只有一个工具 bash，一切外部操作（执行命令、文件读写改、搜索、抓 log 全文）都靠它。能力来自插件、经验来自技能库，全部经 bash + HTTP 调用，不搞多工具路由。
- **生产 = 权威**（多实例时）：插件、配置、提示词以生产树为唯一权威，副本单向镜像跟随；救生艇冻结旧树、永不更新，只用于双死救场。
- **生命自感知**：系统提示词首 prepend 一块"[你的生命]"——本实例端口/PID/源码位置 + 所接入 LLM 服务的端口/PID，每次 LLM 调用现算。明确告诉模型：这些 PID 和端口就是你和你思考的载体，kill/重启/占用它们 = 伤自己的命。
- **署名先于记忆**：agent 的提交必带 `Provenance: agent(<名字> @<端口>)` trailer——账本要先承载"谁写的"，才谈得上承载过去。

## 二、架构亮点

- **上下文滚动压缩**：总 token 超预算时，把旧消息批次交给 LLM 压成总结滚动进 summary；迭代压缩最多 3 轮（单轮 LLM 倾向写长），3 轮后取最短一轮保底；压缩流式可见（WebUI 实时看思考块）。
- **前台超时自动转后台**：工具调用与 30s 前台超时赛跑（`tools.fg_timeout_ms`），超时不取消、转后台继续执行，立即回填"已转后台"通知（tool_calls 与 tool 消息严格配对）；`BackgroundOrchestrator` 持任务表（call_id → settled/ok/耗时/结果副本），goroutine 阻塞在结果通道上，出结果即标记 settled 并把通知 push 进消息队列。通知走两条路：本轮未结束 → 下次 LLM 调用前搭车注入（纯追加，不加 LLM 调用、不动已缓存前缀 → 无额外 KV 代价；后台通知以"（系统通知：后台任务完成"开头，不加【用户追加】前缀，与用户追加同队列不同标记）；本轮已收笔 → 留在队列，下次运行触发。命令总时长另有 `tools.timeout_ms` 硬兜底（到点杀整个进程组）——转后台不是无限放任。
- **轮末校验（end_check）+ 后台任务闸门**：模型输出结束且无 tool_calls（=本轮停止信号）→ 注入校验提示再问一次 → 仍无工具调用才正式收笔（**本轮回复取校验前正文**，不是校验应答），有工具调用则继续干活。每次停止至多校验一次（防追问乒乓），`agent.end_check=false` 全关回到旧行为。措辞即判据（踩坑换来）：旧文案问"有没有还未完成的事情"，模型读成"任务没全完=有"，于是等待期间每次收笔都被推回去；现文案问"此刻有没有必须你现在就做的动作"，把"等待外部结果"明确排除在"有"之外。机制层再加闸门：收笔前查 `Unsettled()`（未 settle 的后台任务数）>0 → 发 `end_check_skipped` 事件直接收笔，连追问都省掉。实测一次 5 GiB 模型下载期间被追问十余次，每次 = 一次完整 LLM 推理，而下载一次都不需要模型。局限：闸门只覆盖经编排器注册的任务，模型自己 `setsid` 完全脱离起的进程不在表内，此类场景靠措辞兜底。
- **死循环检测（doom）**：连续 3 次完全相同（工具名+参数逐字段比较）的调用 → 注入警告；警告后仍重复 → 强停本轮。
- **提示词分层 + 热加载**：通用层（prompts/*.md）拼接为系统提示词，POST /prompts/reload 热加载；专用层（部署拓扑 / 插件规范 / 各插件 README）不进系统提示词，agent 按需 cat。
- **彻底解耦契约**：主程序对插件无感知——不加载、不扫描、不启动；插件不 import 主程序任何模块、不共享进程/内存，只走公开 HTTP 接口（/chat、/enqueue、/events SSE、/history……）；配置自管（插件目录内 config.json）、数据自管（插件/data/）、独立可跑（独立 Go 模块 + 独立 git 仓）。插件挂了不影响 OkHuman，OkHuman 重启不影响插件。
- **scout 语义索引**：Go 常驻服务（:8480）递归扫描插件/技能仓，条目摘要读 agent 自写的 meta.json，打分 = 关键词 + Qwen3-Embedding-0.6B 语义向量。硬规则：需要主程序之外的能力，先搜索引，凭记忆跳过 = 违规（缘由：读图需求没搜索引走了通用 OCR 弯路，而素材注入插件两次都是搜索第一命中）。
- **二进制交换协议 + 保护期**：主程序二进制只换对方实例的运行树；换前先用一次性实例端到端验证；新二进制严禁同时落两棵树——旧二进制实例就是救生艇。换前问一句："此刻如果新二进制有 bug，谁还活着能救？"答不上就不换。

## 三、插件是怎么做的

两个区域（`plugins/RULE.md` 为唯一权威）：

1. **plugins/** —— 插件目录，扁平排列：attach / browser / computer / cron / okmon / qq-channel / scout / voice-chat
2. **plugins/skills/** —— 技能库，日期层级 year_/month_/day_：skill = SKILL.md（本机**实测验证过**的操作经验，照它执行）+ 可选 scripts/references；账号令牌不进技能目录

每个插件是一个**自包含小系统**：

- 独立进程 + 自带 config.json + 自带 data/ + 独立 git 仓
- 目录必带 `README.md`（启动 + 配置 + 排障）和 `meta.json`（agent 自写一句话摘要，scout 索引信号，summary 必填）
- 多实例适配：配置里 `instances[]` 列出每个 OkHuman 实例的 {id, url}，消息按配置路由到对应实例
- 改完源码 = 没干活，**重编 + 真实启动验证 = 才干完**（忘重编曾是一起 bug 复发的根因）
- 改完 README/meta.json → POST /reindex 刷 scout 索引

## 四、部署拓扑（多实例推荐）

- **生产**：权威树，服务 :8451，插件/技能仓在仓根 `plugins/`
- **副本**：另一进程树（如 :8452），插件仓跟随生产瘦镜像（单向 rsync --delete，重资产不镜像）
- **救生艇**：冻结旧树（永不更新），平时不起——唯一用途是生产与副本都死时救场
